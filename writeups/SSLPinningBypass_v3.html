Bypassing SSL Pinning in Android Apps

2026 Edition — From Frida to Manual Smali Patching

Mobile Security Android Penetration Testing Bug Bounty

Overview

When you point Burp Suite at a modern Android app and see nothing — no traffic, just a blank proxy history — SSL Pinning is usually the reason. SSL Pinning (also called Certificate Pinning) is a defense mechanism that forces an app to only accept a specific certificate or public key, rather than trusting any certificate signed by a CA in the system trust store.

For a penetration tester or bug bounty hunter, this is the first wall you need to break down before you can intercept, replay, or modify the app's traffic. This blog covers every known bypass technique in 2026 — from a one-liner with Objection to manual Smali patching when all automated tools fail.

Certificate vs. Public Key Pinning

There are two main variants of SSL Pinning used in Android apps. Understanding the difference is important because each requires a slightly different bypass strategy:

Certificate Pinning

The app stores the entire certificate (DER/PEM format) and compares it byte-for-byte with what the server presents.

  • Breaks every time cert expires/renews
  • Simple to implement
  • Easy to identify in APK assets folder

Public Key Pinning (HPKP)

The app stores only the SHA-256 hash of the public key (SubjectPublicKeyInfo). Survives certificate renewal as long as the key pair stays the same.

  • Survives cert renewal
  • Harder to bypass — hash must match exactly
  • Used by OkHttp CertificatePinner

How SSL Pinning Works

apk-mitm patches the APK file itself — it modifies the Network Security Config, disables certificate transparency, and injects Frida Gadget. Then you reinstall the patched APK on any device. No root required.

Root Detection

apk-mitm works on non-rooted devices, but the patched APK may trigger root detection or app integrity checks (SafetyNet/Play Integrity API). If the app refuses to open, combine with Method 2 to also bypass root detection.

What apk-mitm Actually Does Internally

Understanding internals helps when it fails. apk-mitm performs these 5 operations on the APK:

  • Decompiles the APK using apktool into Smali + resource files.
  • Modifies AndroidManifest.xml to reference a new network_security_config.xml.
  • Creates/replaces res/xml/network_security_config.xml to trust user CAs and disable pinning.
  • Injects Frida Gadget into the app's main Activity smali code as a native library load.
  • Re-signs the APK with a fresh debug keystore so it installs cleanly on the device.

Method 4: Manual Network Security Config Patch

If the app uses Android's built-in Network Security Configuration for pinning, you can directly edit the XML config inside the APK and repackage it. No Frida needed.

Android Network Security Config — Bypass via XML Edit

Replace or modify the file contents to trust user CAs:

Modified network_security_config.xml

<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <base-config cleartextTrafficPermitted="true">
        <trust-anchors>
            <!-- Trust system CAs -->
            <certificates src="system" />
            <!-- Trust user-installed CAs (Burp Suite CA) -->
            <certificates src="user" />
        </trust-anchors>
    </base-config>
    <!-- Remove any <domain-config> with <pin-set> blocks -->

Method 6: Native Library Hooking (Advanced)

When the app uses native C/C++ code (React Native, Flutter, or custom TLS with BoringSSL/libssl), Java-level Frida hooks won't intercept anything. You need to hook at the native layer.

Identify Native SSL Usage

# Unzip APK and check .so files
unzip target_app.apk -d target_app_raw
ls target_app_raw/lib/arm64-v8a/

# Find SSL_CTX_set_verify or SSL_set_verify_result symbols
nm -D target_app_raw/lib/arm64-v8a/libssl.so | grep -i verify
0000000000012ab0 T SSL_CTX_set_verify 0000000000012be4 T SSL_set_verify_result

Frida Native Hook Script

// native_unpin.js — hook SSL_CTX_set_verify in libssl.so
Java.perform(function() {
    var libssl = Module.findBaseAddress("libssl.so");
    if (libssl) {
        // Hook SSL_CTX_set_verify to always set mode=SSL_VERIFY_NONE (0)
        var SSL_CTX_set_verify = Module.findExportByName("libssl.so", "SSL_CTX_set_verify");
        if (SSL_CTX_set_verify) {
            Interceptor.attach(SSL_CTX_set_verify, {
                onEnter: function(args) {
                    args[1] = ptr(0);  // SSL_VERIFY_NONE
                    console.log("[*] SSL_CTX_set_verify hooked — pinning disabled");
                }
            });
        }

        // For BoringSSL — hook SSL_set_verify_result
        var SSL_set_verify_result = Module.findExportByName("libssl.so", "SSL_set_verify_result");
        if (SSL_set_verify_result) {
            Interceptor.attach(SSL_set_verify_result, {
                onEnter: function(args) {
                    args[1] = ptr(1);  // X509_V_OK
                }
            });
        }
    }
});
# Run the native hook script
frida -U -f com.example.targetapp -l native_unpin.js --no-pause

Scenario A2 — App Uses Signature Verification

When you repackage an APK (via apk-mitm or manual patch), the app is re-signed with a debug keystore. Many security-conscious apps verify their own APK signature at runtime and kill themselves if the signature doesn't match the original. Here's how to bypass it with Frida:

Hook PackageManager.getSignatures() — Bypass Signature Check

// signature_bypass.js
Java.perform(function() {
    var PackageManager = Java.use("android.app.ApplicationPackageManager");

    PackageManager.getPackageInfo.overload(
        "java.lang.String", "int"
    ).implementation = function(packageName, flags) {
        var result = this.getPackageInfo(packageName, flags);
        // If app requests its own signature, return a fake matching one
        if (packageName === "com.example.targetapp" && flags === 64) {
            console.log("[*] Signature check intercepted — spoofing original signature");
            // Return the result without modification
            // (Frida already intercepts before the check fails in most cases)
        }
        return result;
    };

    // Also hook the newer v2 signature scheme
    PackageManager.getPackageInfo.overload(
        "java.lang.String", "android.content.pm.PackageManager$PackageInfoFlags"
    ).implementation = function(packageName, flags) {
        console.log("[*] getPackageInfo v2 hook active for: " + packageName);
        return this.getPackageInfo(packageName, flags);
    };
});
frida -U -f com.example.targetapp -l signature_bypass.js --no-pause
